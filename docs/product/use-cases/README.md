# Use Cases

Settled product behavior, precise enough to build against — the handoff from product to engineering (see [`../product-operating-model.md`](../product-operating-model.md)). Use [`UC-TEMPLATE.md`](UC-TEMPLATE.md) for new ones.

This index is also the record of **what the product does today**. Backlog items leave the [backlog](../product-backlog.md) when they are built; the row of the use case that absorbed them keeps their IDs, so an old reference such as "P0-007" can always be traced here.

## Statuses

- **Draft** — being shaped; not ready to build.
- **Approved** — settled; the implementation gate for Level 2+ work.
- **Implemented** — the behavior is built and merged on at least one surface. Not the same as released, and not the same as "a user can do this": read the Surfaces column for that.

## Surfaces

Buyers, sellers, and operators use the web app; the API is how it is built, not how they reach it. The Surfaces column records where a use case is actually exercisable today, so a use case built API-first cannot read as finished:

- **API** — the backend behavior is built and tested over HTTP.
- **Web** — a user can perform the use case in `apps/web`.
- **—** — that surface does not exist yet; the gaps column names the roadmap slice that adds it.

A use case is only complete when every surface it names is filled. Use cases whose Primary Actor is a person always name both; a use case can be API-only by design only when its actor is a system or an external integration, and must say so in its Scope decisions.

Update a row in the same PR that changes its use case's status, fills a surface, absorbs backlog items, or opens or closes a gap. Gaps are places where the built behavior falls short of the use case; follow-ups are deferred work tracked in the backlog. A Level 1 improvement that amends a use case adds its backlog ID to that use case's row.
